# REVIEW.md

I reviewed the starter file against the API contract and tested the main failure cases while implementing the missing functionality. The issues below were the ones that needed attention.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` | The endpoint returns `ok` without checking whether MongoDB is reachable. | Stop MongoDB and call `/health`; it can still report success. | Added a MongoDB ping and return an error response when the database is unavailable. |
| 2 | `compute_late_minutes()` | The calculation replaces the punch-in time's hour and minute instead of constructing the shift start on the correct IST attendance date. It also loses the seconds needed for the grace-period boundary. | With a 09:30 shift, a punch-in at 09:40:01 should count as 10 late minutes, not zero. | Calculate the shift start using the attendance date and IST, compare elapsed seconds, then apply the strict 10-minute grace rule. |
| 3 | `compute_work_hours()` | Python's built-in `round()` does not guarantee the required half-up rounding. | Test a duration whose hour value falls exactly on a half-cent boundary. | Used `Decimal` with `ROUND_HALF_UP` and rounded the elapsed seconds divided by 3600 to two decimal places. |
| 4 | `compute_overtime()` | The original helper ignores the shift start, does not handle overnight shifts, and counts overtime before the required 30-minute threshold. | For a 09:30-18:30 shift, leaving at 18:45 should give zero overtime; leaving at 19:00 should give 30 minutes. | Calculate the correct shift-end datetime, advance the end date for overnight shifts, and count whole minutes only after the threshold is met. |
| 5 | `create_employee()` | Checking for an existing employee before inserting is not safe when two requests arrive together. | Send simultaneous requests using the same `emp_code`; both can pass the initial check. | Added a unique index on `emp_code` and handled `DuplicateKeyError` as a 409 conflict. |
| 6 | `create_employee()` / `EmployeeIn` | The starter does not adequately validate employee fields, shift times, or the relationship between shift start and shift end. It also creates a naive timestamp. | Try malformed dates, invalid shift times, or identical shift start and end values. | Added request validation and used a UTC-aware server timestamp for `created_at`. |
| 7 | `list_employees()` | The offset is calculated as `page * page_size`, which skips the first page. The total count also ignores the department filter, and results are not explicitly sorted. | Request page 1 with page size 2; the first two employees are skipped. Filter by department and compare `total`. | Changed the offset to `(page - 1) * page_size`, counted the filtered query, sorted by `emp_code`, and constrained pagination inputs. |
| 8 | `punch_in()` | A missing employee is not handled before accessing its shift fields. The timestamp also depends on the machine's local timezone, and a value of zero is treated as if no timestamp was supplied. | Punch in for an unknown employee or send an invalid timestamp. | Check that the employee exists, normalize timestamps to UTC, distinguish `None` from numeric values, and validate the request. |
| 9 | `punch_in()` | The existence check followed by an insert is vulnerable to concurrent requests. The original code also returns MongoDB's internal ID, which is outside the API contract. | Send two punch-ins for the same employee and date, or inspect the response for an `id` field. | Enforced uniqueness on `(emp_code, date)`, translated duplicate-key errors to 409, and returned the contract fields without exposing `_id`. |
| 10 | `list_attendance()` | The starter loads matching documents into Python, sorts them there, and only then paginates. This uses unnecessary memory and does not scale to 100,000 records. | Run the endpoint against a large collection and inspect memory usage and response time. | Moved sorting, skipping, and limiting into MongoDB, added suitable indexes, and used the filtered query for the total count. |
| 11 | `list_attendance()` | Pagination inputs and status values are not adequately validated, and the response exposes internal IDs instead of consistently serializing API fields. | Send `page_size=101`, an invalid status, or inspect the response fields. | Added pagination bounds and status validation, excluded `_id`, and serialized timestamps and optional fields according to the contract. |
| 12 | `create_indexes()` / startup | The starter does not create the indexes needed for uniqueness and efficient list and analytics queries. | Start with a fresh database or inspect query plans and duplicate behavior. | Added idempotent startup index creation for employee identity, attendance identity, date-based listing, department/join-date queries, and late-attendance filtering. |
| 13 | Remaining endpoints | The starter leaves punch-out, regularization, monthly analytics, department summary, late leaderboard, department trend, and explain functionality unimplemented. | Call the documented paths; the starter has no corresponding endpoint implementations. | Implemented the missing endpoints, using MongoDB aggregation for analytics and conditional updates for attendance changes. |

## Checked and retained

- **Employee identity:** `emp_code` remains the business identifier. MongoDB `_id` is internal and is not returned by the API.
- **Attendance uniqueness:** A record is identified by `(emp_code, date)`, so a unique compound index is appropriate.
- **Missing attendance records:** A weekday with no attendance record is different from an explicit `ABSENT` record. The analytics should not treat these as interchangeable.
- **Regularization history:** History is reserved for manual corrections. Normal punch-in and punch-out operations should not add audit entries.
- **Derived attendance fields:** Work hours, late minutes, overtime minutes, and half-day status are calculated by the API rather than accepted from clients.

The main lesson from this review was that the happy path was not enough. The implementation also needed correct boundary handling, database-enforced uniqueness, bounded pagination, and queries that remain efficient as the collection grows.
